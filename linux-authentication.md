## 1.1. Вход пользователя на сервер по SSH

```text
1. Пользователь → SSH-соединение на сервер (порт 22)
   ↓
2. /etc/ssh/sshd_config
   "вообще можно ли root по SSH?" → PermitRootLogin no
   "на каком порту слушать?" → Port 22
   "какие методы аутентификации?" → PasswordAuthentication, PubkeyAuthentication
   ↓
3. /etc/pam.d/sshd  (сценарий PAM для SSH-сервиса)
   Подключает через @include:
   - common-auth      (проверка пароля)
   - common-account   (можно ли аккаунту входить?)
   - common-session   (что делать после входа)
   ↓
4. /etc/pam.d/common-account
   "этому пользователю с этого IP можно?" → pam_access.so
        ↓
        /etc/security/access.conf
        +:root:LOCAL
        +:local-admin:LOCAL
        +:admins-group:ALL
        -:ALL:ALL
   ↓
5. /etc/pam.d/common-auth
   "как проверить пароль?" — по порядку:
   ├─ pam_faillock.so preauth    → не заблокирован ли уже?
   │       ↓
   │       /etc/security/faillock.conf
   │       deny = 5, unlock_time = 900
   │
   ├─ pam_unix.so                → локальный пароль (из /etc/shadow)
   ├─ pam_sss.so                 → пароль в LDAP (через SSSD)
   │       ↓
   │       /etc/sssd/sssd.conf
   │       ldap_uri = ldap://ldap-server:389
   │       ldap_default_bind_dn = cn=ldap-reader,...
   │
   └─ pam_faillock.so authfail / authsucc
           "неудача → увеличить счётчик" / "успех → сбросить счётчик"
                ↓
                /var/lib/faillock/  (файлы счётчиков)
   ↓
6. Пароль верный → пользователь вошёл → создаётся сессия
   ↓
7. /etc/pam.d/common-session
   "что сделать после входа?"
   - создать домашнюю директорию
   - смонтировать /home (если нужно)
   - установить переменные окружения
   - запустить скрипты из /etc/profile.d/
   ↓
8. Пользователь выполняет sudo <команда>
   ↓
9. /etc/pam.d/sudo
   "как проверить, можно ли sudo?"
   Подключает @include common-auth (снова проверка пароля!)
   ↓
10. /etc/sudoers  +  /etc/sudoers.d/ldap-sudo
    "а можно ли ему sudo и на что?"
    %admins-group ALL=(ALL:ALL) ALL
    local-admin ALL=(ALL) /usr/bin/systemctl, /usr/bin/passwd, ...
    ↓
    Проверка: входит ли пользователь в группу %admins-group?
    Откуда берётся группа?
        ↓
        LDAP: cn=admins-group,ou=Groups,dc=example,dc=com
        (через SSSD + NSS: /etc/nsswitch.conf → group: files sss)
   ↓
11. Разрешено → команда выполняется от root
```

## 1.2. Смена пароля

```text
1. Пользователь выполняет passwd (или меняет пароль через GUI/SSH)
   ↓
2. /etc/pam.d/passwd  →  @include common-password
   ↓
3. /etc/pam.d/common-password
   "как проверить новый пароль?" — по порядку:
   ├─ pam_pwquality.so retry=3 enforce_for_root
   │       ↓
   │       /etc/security/pwquality.conf
   │       minlen = 8, minclass = 3, maxrepeat = 3, usercheck = 1
   │
   ├─ pam_pwhistory.so use_authtok
   │       ↓
   │       /etc/security/pwhistory.conf
   │       remember = 3, enforce_for_root
   │
   ├─ pam_unix.so   → сохранить локальный хеш в /etc/shadow
   │       ↓
   │       /etc/login.defs
   │       PASS_MAX_DAYS 180, PASS_MIN_DAYS 0,
   │       PASS_WARN_AGE 7, ENCRYPT_METHOD SHA512
   │
   └─ pam_sss.so use_authtok   → отправить новый пароль в LDAP
           ↓
           LDAP: ldap-server (ou=Users,dc=example,dc=com)
           тут срабатывает ppolicy:
               ↓
               cn=default / pwdPolicyUsers / pwdPolicyService
               pwdMinLength: 8, pwdInHistory: 3,
               pwdMaxAge: 15552000, pwdCheckModule: check_password.so
   ↓
4. Все проверки пройдены → пароль изменён (и локально, и в LDAP)
```

## 1.3. Блокировка учётки в LDAP (ppolicy)

Это происходит **не на хосте**, а **внутри ldap-server**, когда любой хост пытается проверить пароль доменной учётки:

```text
1. Пользователь вводит пароль на workstation
   ↓
2. workstation: /etc/pam.d/common-auth → pam_sss.so
   "спроси у LDAP, верный ли пароль?"
   ↓
3. По сети: ldap://ldap-server:389
   ↓
4. ldap-server: OpenLDAP + overlay ppolicy
   "проверяю пароль + смотрю счётчик неудач"
        ↓
        /opt/ldap-policy/*.ldif  (шаблоны, применены через start.sh)
        ↓
        База mdb (реальные политики):
        - cn=default,ou=Policies
        - cn=pwdPolicyUsers,ou=Policies
        - cn=pwdPolicyService,ou=Policies
        ↓
   Если пароль неверный:
        pwdFailureCount++ (в атрибуте pwdFailureTime учётки)
   Если pwdFailureCount >= pwdMaxFailure (5):
        учётка блокируется на pwdLockoutDuration (900 сек)
   ↓
5. Ответ в workstation: "OK" или "заблокирован"
```

## 2.1. Сводная таблица ключевых файлов и их ролей

| Путь | Что определяет |
| :--- | :--- |
| `/etc/ssh/ssh_config` | Конфигурация клиента (программы ssh). Определяет, как клиент подключается к другим серверам: алгоритмы шифрования, сжатие, настройки по умолчанию. На безопасность самого сервера не влияет. |
| `/etc/ssh/sshd_config` | Конфигурация сервера (демона sshd). Определяет, как сервер принимает входящие подключения: порт, PermitRootLogin, методы аутентификации, логирование. |
| `/etc/pam.d/sshd` | Сценарий PAM для SSH (подключает common-*) |
| `/etc/pam.d/common-account` | Проверка: можно ли аккаунту входить (`pam_access`) |
| `/etc/security/access.conf` | Белый список «кто откуда может входить» |
| `/etc/pam.d/common-auth` | Проверка пароля при входе (`pam_faillock`, `pam_unix`, `pam_sss`) |
| `/etc/security/faillock.conf` | Параметры блокировки (5 попыток, 900 сек) |
| `/var/lib/faillock/` | Файлы счётчиков неудачных попыток (по пользователям) |
| `/etc/pam.d/common-session` | Действия после входа (домашняя папка, окружение) |
| `/etc/pam.d/sudo` | Сценарий PAM для `sudo` (переиспользует common-auth) |
| `/etc/sudoers` + `/etc/sudoers.d/*` | Кто и что может через `sudo` |
| `/etc/sssd/sssd.conf` | Связь с LDAP (URI, bind DN, схема) |
| `/etc/nsswitch.conf` | Откуда брать пользователей/группы (`files sss`) |
| `/etc/pam.d/passwd` | Сценарий PAM для смены пароля |
| `/etc/pam.d/common-password` | Смена пароля (`pam_pwquality`, `pam_pwhistory`, `pam_sss`) |
| `/etc/security/pwquality.conf` | Требования к сложности пароля |
| `/etc/security/pwhistory.conf` | История паролей |
| `/etc/login.defs` | Сроки действия пароля, метод шифрования |
| `/opt/ldap-policy/*.ldif` | Шаблоны LDAP-политик (применяет `start.sh`) |
| База `mdb` (LDAP) | Рабочие политики `ppolicy` (`cn=default`, `pwdPolicyUsers`, `pwdPolicyService`) |
| `/usr/bin/start.sh` | Что происходит при старте контейнера `ldap-server` |

## 2.2. Взаимодействие `/etc/pam.d/` и `/etc/security/`

Выполняют разные роли в одном механизме — `архитектуре PAM`:

**`/etc/pam.d/` (Сценарий проверки):**
Здесь лежат файлы для каждого сервиса (sshd, login, su, sudo, common-*). Эти файлы — сценарий того, какие шаги проверки нужно выполнить для этого сервиса. Например, в `common-auth` написано: «сначала проверь блокировку (`pam_faillock`), потом пароль по локальной базе (`pam_unix`), потом по LDAP (`pam_sss`)». Это порядок действий и список модулей.

**`/etc/security/` (Правила игры):**
Здесь лежат конфигурационные файлы для этих модулей. Они определяют детали работы: `faillock.conf` говорит «блокировать после 5 попыток», `pwquality.conf` говорит «минимальная длина 8 символов», `access.conf` говорит «кому можно входить». Это параметры и правила.

---
## 2.3. Где находится `pam_pwquality.so`

Модуль — часть пакета `libpam-pwquality`.

> `pam_pwquality.so` — это «движок», который умеет проверять. Он не знает, каким должен быть параметр. Его задача — выполнить проверку по заданным правилам. `/etc/security/pwquality.conf` — это файл с правилами (политика). Именно здесь написано, что «пароль должен быть не короче 8 символов» (`minlen = 8`) и «содержать минимум 3 класса символов» (`minclass = 3`).

В разных дистрибутивах Linux путь может немного отличаться, но обычно он лежит в директории с PAM-модулями:

*   **Debian/Ubuntu**: 
    `/lib/x86_64-linux-gnu/security/pam_pwquality.so` или `/usr/lib/x86_64-linux-gnu/security/pam_pwquality.so`.
*   **RHEL/Fedora/CentOS**: 
    `/usr/lib64/security/pam_pwquality.so`.

## 2.4. Справка по директориям

### 📁 `/etc/ssh/`
*   **`sshd_config`**: Конфигурация **SSH-сервера**. Определяет, как сервер принимает входящие подключения (порт, разрешён ли вход root, методы аутентификации).
*   **`ssh_config`**: Конфигурация **SSH-клиента**. Определяет, как клиент подключается к другим серверам (алгоритмы шифрования, сжатие).

### 📁 `/etc/pam.d/` (Сценарии для сервисов)
Каждый файл здесь — это **сценарий**, какие проверки выполнить для конкретного сервиса. Файлы `common-*` — это общие сценарии, которые подключаются (`@include`) из других файлов.

*   **`common-auth`**: Сценарий **проверки пароля при входе**. Определяет, какие модули (например, `pam_unix.so`, `pam_sss.so`, `pam_faillock.so`) и в каком порядке должны проверить подлинность пользователя.
*   **`common-account`**: Сценарий **проверки допустимости входа**. Определяет, можно ли аккаунту входить в систему (не истёк ли срок действия пароля, не заблокирован ли он, разрешён ли вход по времени/группе через `pam_access.so`).
*   **`common-password`**: Сценарий **смены пароля**. Определяет, какие модули (например, `pam_pwquality.so`, `pam_pwhistory.so`) должны проверить новый пароль перед его установкой.
*   **`common-session`**: Сценарий **действий после входа**. Определяет, что нужно сделать после успешной аутентификации (создать домашнюю директорию, смонтировать файловые системы, установить переменные окружения).
*   **`sshd`**: Сценарий PAM специально для **SSH-сервера**. Обычно просто подключает `common-auth`, `common-account` и `common-session`.
*   **`su` / `su-l`**: Сценарий для команды **`su`** (переключение пользователя). Может содержать дополнительные проверки (например, через `pam_wheel.so`, разрешая `su` только членам группы `sudo`).
*   **`sudo`**: Сценарий для команды **`sudo`**. Подключает `common-auth` для повторной проверки пароля пользователя.
*   **`login`**: Сценарий для входа через **консоль** (tty).
*   **`cron`**: Сценарий для заданий **планировщика**.
*   **`other`**: Сценарий по умолчанию для сервисов, у которых нет собственного файла.

### 📁 `/etc/security/` (Правила для модулей PAM)
Каждый файл здесь — это **конфигурация** для конкретного модуля PAM, определяющая параметры его работы.

*   **`access.conf`**: Правила **доступа к системе**. Определяет, каким пользователям и группам разрешён или запрещён вход на хост. Используется модулем `pam_access.so`.
*   **`faillock.conf`**: Правила **блокировки после неудачных попыток входа**. Определяет, после скольких неудач блокировать учётную запись и на какое время. Используется модулем `pam_faillock.so`.
*   **`pwquality.conf`**: Правила **сложности пароля**. Определяет минимальную длину, требуемые классы символов и другие параметры. Используется модулем `pam_pwquality.so`.
*   **`pwhistory.conf`**: Правила **истории паролей**. Определяет, сколько последних паролей нужно помнить и запрещать к повторному использованию. Используется модулем `pam_pwhistory.so`.
*   **`limits.conf`**: Ограничения **системных ресурсов** для пользователей (например, максимальное количество процессов, размер файлов).
*   **`group.conf`**: Ограничения, применяемые к **группам** пользователей.
*   **`time.conf`**: Ограничения по **времени входа** для определённых сервисов.
*   **`pam_env.conf`**: Установка **переменных окружения** при входе пользователя.

---
## 2.5. Цепочки процессов (кто кого вызывает)

*   **Вход по SSH:**
    > **ssh** → **sshd_config** → **PAM (account → auth → session)** → **sudo**
*   **Смена пароля:**
    > **passwd** → **common-password** → **pwquality → pwhistory → SSSD → LDAP**
*   **Блокировка в LDAP:**
    > **любой хост** → **pam_sss** → **LDAP** → **ppolicy** → **счётчик + lockout**

## 3. Управление доступом: `access.conf` и `sudoers`

Разбираем синтаксис, логику построения и все варианты для двух ключевых файлов ограничения доступа.

---
## 3.1. `access.conf` — «Кто откуда может входить»

### 3.1.1. Где лежит и кто читает
```text
/etc/security/access.conf
        ↓ читает
/etc/pam.d/common-account  →  account required pam_access.so
        ↓
Применяется при ЛЮБОМ входе: SSH, консоль, su, login, cron
```
**Важно:** `access.conf` проверяется на этапе `account` (после того, как пароль уже введён, но до создания сессии). То есть: «пароль верный, но **этому пользователю с этого адреса** входить нельзя».

### 3.1.2. Синтаксис строки
**Формат:** `<действие>:<пользователи>:<откуда>` (Три поля, разделённые двоеточием `:`).

Разбор строки `+:localadmin:ALL`:
```text
+        :  localadmin  :  ALL
│           │              │
│           │              └── ОТКУДА можно входить
│           └───────────────── КОМУ разрешено
└───────────────────────────── ДЕЙСТВИЕ (разрешить)
```

| Поле | Что значит | Варианты |
| :--- | :--- | :--- |
| **Действие** | Разрешить или запретить | `+` (разрешить), `-` (запретить) |
| **Пользователи** | Кому применяется правило | имя, группа `(group)`, `@netgroup`, `ALL`, `EXCEPT` |
| **Откуда** | С какого адреса/терминала | `ALL`, `LOCAL`, `NONE`, IP, сеть, имя хоста, домен, `ttyN` |

### 3.1.3. Поле 1: Действие (`+` / `-`)
```text
+:...  → разрешить
-:...  → запретить
```
**Логика:** файл читается **сверху вниз**. Срабатывает **первое** совпавшее правило. Дальше не проверяется.

```text
1. +:root:LOCAL              ← root с консоли — разрешить
2. +:localadmin:LOCAL        ← localadmin с консоли — разрешить
3. +:sg-linux-admins:ALL     ← админам систем — отовсюду
4. -:ALL:ALL                 ← всем остальным — запретить
```

### 3.1.4. Поле 2: Пользователи
| Синтаксис | Что значит | Пример |
| :--- | :--- | :--- |
| `root` | Конкретный пользователь | `+:root:LOCAL` |
| `localadmin` | Конкретный пользователь | `+:localadmin:LOCAL` |
| `(wheel)` | **Группа** (в скобках) | `+:(wheel):ALL` |
| `sg-linux-admins` | **Группа без скобок** — если имя группы не совпадает с именем пользователя | `+:sg-linux-admins:ALL` |
| `@netgroup` | Netgroup (NIS/NIS+) | `+:@admins:ALL` |
| `ALL` | Все пользователи | `+:ALL:LOCAL` |
| `ALL EXCEPT root` | Все, кроме root | `+:ALL EXCEPT root:LOCAL` |
| `user1 user2 user3` | Несколько через пробел | `+:root localadmin:LOCAL` |

**Ключевой нюанс: `(group)` vs `group`**
```text
+:(wheel):ALL     ← ЭТО ГРУППА (скобки указывают «это группа»)
+:wheel:ALL       ← ЭТО ПОЛЬЗОВАТЕЛЬ (если есть пользователь wheel)
```

### 3.1.5. Поле 3: Откуда (`origins`)
| Синтаксис | Что значит | Когда срабатывает |
| :--- | :--- | :--- |
| `ALL` | Откуда угодно | SSH, консоль, cron, любые IP |
| `LOCAL` | **Только с консоли** | `tty`/`vc` (без точки в имени). Не срабатывает для SSH |
| `NONE` | Ниоткуда | Правило никогда не сработает (для отключения) |
| `tty1` | Конкретный терминал | Только с `tty1` |
| `tty*` | Все tty | Все консольные терминалы |
| `192.168.201.199` | Конкретный IP | Только с этого IP |
| `192.168.201.` | Подсеть (строковое совпадение) | IP, начинающиеся с `192.168.201.` |
| `192.168.201.0/24` | Подсеть (CIDR) | Все IP из подсети |
| `192.168.201.0/255.255.255.0` | Подсеть (netmask) | То же самое |
| `.local.host` | Домен (начинается с точки) | Хосты из домена `local.host` |
| `hostname` | Конкретный хост | Только с этого хоста |
| `LOCAL .example.com` | Несколько через пробел | Консоль **или** хосты из домена |
| `ALL EXCEPT LOCAL` | Все, кроме консоли | Только удалённые подключения |

**Ключевой нюанс: `LOCAL` vs `ALL`**
```text
LOCAL  ← только консоль (tty, vc, console)
       ← НЕ срабатывает для SSH, cron, su
       ← «физический доступ к машине»

ALL    ← откуда угодно
       ← SSH, консоль, cron, su, любые IP
       ← «любой способ входа»
```

## 3.2. `sudoers` — «Что можно делать через sudo»

### 3.2.1. Где лежит и кто читает
```text
/etc/sudoers              ← основной файл (не трогаем напрямую)
        ↓
/etc/sudoers.d/           ← директория с дополнительными файлами
        ↓
/etc/sudoers.d/ldap-sudo  ← наш файл
```
**Важно:** файлы в `/etc/sudoers.d/` **подключаются** из `/etc/sudoers` через строку `@includedir /etc/sudoers.d`.
**Права:** файлы должны быть `0440 root:root`. Иначе `sudo` их **проигнорирует** (защита от подмены).
**Проверка синтаксиса:** `visudo -cf /etc/sudoers.d/ldap-sudo` → `parsed OK`.

### 3.2.2. Синтаксис строки
**Формат:** `<КТО> <ГДЕ>= (<ОТ_КОГО>:<ОТ_ГРУППЫ>) <ЧТО>`

Разбор строки `localadmin ALL=(ALL:ALL) ALL`:
```text
localadmin        ALL=(ALL:ALL)        ALL
│                 │   │   │            │
│                 │   │   │            └── ЧТО можно запускать
│                 │   │   └─────────────── ОТ ИМЕНИ КАКОЙ ГРУППЫ
│                 │   └─────────────────── ОТ ИМЕНИ КАКОГО ПОЛЬЗОВАТЕЛЯ
│                 └─────────────────────── ГДЕ (на каком хосте)
└───────────────────────────────────────── КТО (пользователь/группа)
```

| Поле | Что значит | Варианты |
| :--- | :--- | :--- |
| **КТО** | Кому разрешено | `user`, `%group`, `User_Alias`, `#uid`, `%#gid` |
| **ГДЕ** | На каком хосте | `ALL`, `hostname`, `Host_Alias`, `192.168.1.1` |
| **(ОТ_КОГО)** | От имени какого пользователя | `ALL`, `root`, `postgres`, `Runas_Alias` |
| **(ОТ_ГРУППЫ)** | От имени какой группы | `ALL`, `root`, `wheel` |
| **ЧТО** | Какие команды | `ALL`, `/usr/bin/systemctl`, `Cmnd_Alias` |

### 3.2.3. Поле 1: КТО
| Синтаксис | Что значит | Пример |
| :--- | :--- | :--- |
| `localadmin` | Конкретный пользователь | `localadmin ALL=(ALL) ALL` |
| `%sg-linux-admins` | **Группа** (с `%`) | `%sg-linux-admins ALL=(ALL:ALL) ALL` |
| `%#1000` | Группа по GID | `%#1000 ALL=(ALL) ALL` |
| `#1000` | Пользователь по UID | `#1000 ALL=(ALL) ALL` |
| `User_Alias ADMINS = user1, user2` | Алиас (группа пользователей) | `ADMINS ALL=(ALL) ALL` |

**Ключевой нюанс:** `%` перед именем = «это группа». Без `%` = «это пользователь».
```text
%sg-linux-admins ALL=(ALL:ALL) ALL   ← ГРУППА
localadmin ALL=(ALL:ALL) ALL         ← ПОЛЬЗОВАТЕЛЬ
```

### 3.2.4. Поле 2: ГДЕ (Host)

```text
ALL              ← на любом хосте (для локального файла = «на этом хосте»)
hostname         ← на конкретном хосте
192.168.1.1      ← по IP
Host_Alias       ← алиас
```

**Для локального хоста:** `ALL` можно использовать, потому что файл лежит в `/etc/sudoers.d/` **конкретного хоста** (в нашем случае `srv_ldap`). То есть «на любом хосте, где есть этот файл» = файл есть только на `srv_ldap`. 

> ### Три сценария, где указание конкретного хоста в поле «ГДЕ» важно.


> #### Сценарий А. Централизованный sudoers (самый частый в проде)
>
> В крупных компаниях `sudoers` не лежит локально на каждом хосте. Он хранится:
> - В LDAP (через `sudo-ldap` или SSSD).
> - На NFS-шаре, которая смонтирована на всех хостах как `/etc/sudoers.d/`.
> - В Ansible/Puppet/Chef — один шаблон, раскатывается на все хосты.
> 
> **Пример:** один и тот же файл `ldap-sudo` лежит на `srv_ldap`, `srv_bastion`, `srv_fs`, `ws_msk_*`. В нём написано:
> ```sudoers
> %SG-ADM-T1-SRV-LINUX-ADMINS srv_ldap,srv_bastion=(ALL) /usr/bin/systemctl
> %SG-ADM-T1-SRV-LINUX-ADMINS srv_fs=(ALL) /usr/bin/systemctl restart smbd
> ```
> **Смысл:** админы Linux-серверов могут перезапускать *любые* сервисы на `srv_ldap` и `srv_bastion`, но на `srv_fs` — *только* `smbd`. Один файл, разные правила для разных хостов.

---


> #### Сценарий Б. Защита от копирования файла (предохранитель)
> Представь: админ по ошибке скопировал `ldap-sudo` с `srv_ldap` на `ws_msk_000019`. 
> 
> **Если в файле написано:**
> ```sudoers
> %sg-linux-admins ALL=(ALL:ALL) ALL
> ```
> — то на рабочей станции члены группы `sg-linux-admins` получат полный root. **Катастрофа.**
> 
> **А если написано:**
> ```sudoers
> %sg-linux-admins srv_ldap=(ALL:ALL) ALL
> ```
> — то на `ws_msk_000019` это правило не сработает (потому что хост не `srv_ldap`). Админ ошибся с копированием, но катастрофы нет. Поле «ГДЕ» — это отличный предохранитель от человеческой ошибки.

---


> #### Сценарий В. Один хост — разные роли
> Бывает, что хост выполняет несколько ролей. Например, `srv_bastion` — это и бастион (точка входа), и DNS-сервер. 
> 
> **В sudoers пишем:**
> ```sudoers
> %SG-ADM-T1-NET-ADMINS bastion=(ALL) /usr/sbin/nft
> %SG-ADM-T1-SRV-DNS-ADMINS bastion=(ALL) /usr/sbin/named
> ```
> **Смысл:** один хост, но разные группы получают разные права в зависимости от роли. Без поля «ГДЕ» пришлось бы делать два отдельных файла.


### 3.2.5. Поле 3: `(ОТ_КОГО:ОТ_ГРУППЫ)` — Runas_Spec
Это **самое непонятное** поле. Оно определяет: **от имени кого** можно выполнить команду.

| Синтаксис | Что значит | Пример использования |
| :--- | :--- | :--- |
| `(ALL:ALL)` | От имени **любого пользователя** и **любой группы** | `localadmin ALL=(ALL:ALL) ALL` — полный root |
| `(ALL)` | От имени любого пользователя, группа по умолчанию | `localadmin ALL=(ALL) ALL` — то же, но группа не указана |
| `(root)` | Только от имени root | `user ALL=(root) /usr/bin/systemctl` |
| `(root:root)` | Только от root, группа root | `user ALL=(root:root) /usr/bin/systemctl` |
| `(postgres)` | Только от имени postgres | `user ALL=(postgres) /usr/bin/psql` |
| `(:wheel)` | От любого пользователя, но группа `wheel` | `user ALL=(:wheel) ALL` |
| `(ALL,!root)` | От любого, **кроме** root | `user ALL=(ALL,!root) ALL` — не может стать root |
| `(ALL:ALL) NOPASSWD:` | Без пароля | `user ALL=(ALL:ALL) NOPASSWD: ALL` |

**Что значит `(ALL:ALL)`:**
```text
(ALL : ALL)
 │     │
 │     └── ГРУППА: можно выполнять от имени любой группы
 └──────── ПОЛЬЗОВАТЕЛЬ: можно выполнять от имени любого пользователя
```
**На практике:** `(ALL:ALL)` = «можно стать **кем угодно**, включая root, включая смену группы».

**Примеры:**
```bash
sudo -u postgres psql          # (ALL) позволяет — «стать postgres»
sudo -g wheel ls               # (ALL:ALL) позволяет — «выполнить с группой wheel»
sudo su -                      # (ALL:ALL) позволяет — «стать root»
```
**Почему `(ALL:ALL)` опасно:** `localadmin ALL=(ALL:ALL) ALL` означает:
- `sudo su -` → **полный root**
- `sudo -u postgres psql` → **стать postgres** (доступ к БД)
- `sudo -g docker bash` → **стать в группе docker** (обход ограничений)
То есть это **не «sudo для админа»**, а «**полный контроль над системой**». Поэтому в аудите мы отметили это как избыточное.

### 3.2.6. Поле 4: ЧТО (Cmnd_Spec)
| Синтаксис | Что значит | Пример |
| :--- | :--- | :--- |
| `ALL` | **Любые команды** | `localadmin ALL=(ALL:ALL) ALL` |
| `/usr/bin/systemctl` | Конкретная команда | `localadmin ALL=(ALL) /usr/bin/systemctl` |
| `/usr/bin/systemctl restart` | Команда с аргументом | `user ALL=(ALL) /usr/bin/systemctl restart nginx` |
| `/usr/bin/systemctl restart *` | Любой аргумент | `user ALL=(ALL) /usr/bin/systemctl restart *` |
| `ALL, !/bin/su` | Все, кроме `su` | `user ALL=(ALL) ALL, !/bin/su` |
| `Cmnd_Alias SERVICES = /usr/bin/systemctl, /usr/bin/service` | Алиас | `user ALL=(ALL) SERVICES` |

**Ключевой нюанс: полный путь обязателен.**
```text
/usr/bin/systemctl     ← ПРАВИЛЬНО (полный путь)
systemctl              ← НЕПРАВИЛЬНО (sudo не найдёт)
```

**Ключевой нюанс: аргументы.**
```text
/usr/bin/systemctl              ← разрешает ЛЮБЫЕ аргументы (restart, stop, status, ...)
/usr/bin/systemctl restart      ← разрешает ТОЛЬКО `systemctl restart` (без указания сервиса)
/usr/bin/systemctl restart *    ← разрешает `systemctl restart <любой сервис>`
```
**Опасность:** `/usr/bin/systemctl` без ограничения аргументов = «можно перезапустить **любой** сервис» = «можно остановить sshd» = «можно потерять доступ».
**Более безопасно:** `/usr/bin/systemctl restart nginx` — только nginx.

### 3.2.7. Специальные директивы
*   **`NOPASSWD` — без пароля**
    ```sudoers
    user ALL=(ALL) NOPASSWD: ALL
    ```
    > Выполнять **без ввода пароля**. Используется для автоматизации (Ansible, cron).
*   **`PASSWD` — с паролем (по умолчанию)**
    ```sudoers
    user ALL=(ALL) PASSWD: ALL
    ```
    > То же, что без указания — требует пароль.
*   **`NOEXEC` — запрет на запуск дочерних процессов**
    ```sudoers
    user ALL=(ALL) NOEXEC: /usr/bin/less
    ```
    > `less` не сможет запустить shell (`!sh`). Защита от «выхода из ограниченной команды».
*   **`SETENV` — разрешить менять переменные окружения**
    ```sudoers
    user ALL=(ALL) SETENV: ALL
    ```
    > Разрешить `sudo -E` (сохранить переменные). По умолчанию запрещено.
*   **`!` — отрицание**
    ```sudoers
    user ALL=(ALL) ALL, !/bin/su, !/usr/bin/passwd
    ```
    > Всё можно, **кроме** `su` и `passwd`.

### 3.2.8. Итоговая таблица: что мы имеем и что можно улучшить
| Строка | Сейчас | Проблема | Рекомендация |
| :--- | :--- | :--- | :--- |
| `%sg-linux-admins ALL=(ALL:ALL) ALL` | Полный root | Избыточно: админам каталога не нужен полный root | `%sg-linux-admins ALL=(ALL) /usr/bin/ldapadd, /usr/bin/ldapmodify, ...` |
| `localadmin ALL=(ALL:ALL) ALL` | Полный root | По Инструкции — допустимо, но избыточно | `localadmin ALL=(ALL) /usr/bin/systemctl, /usr/bin/passwd, /usr/bin/apt, /usr/sbin/sshd` |

**Но:** Ansible-проверка (`test_p.yaml`) ожидает **именно** `ALL=(ALL:ALL) ALL` для `localadmin` (по Инструкции). Если урежем — проверка покажет `NOT OK`. Поэтому оставляем как есть, а рекомендацию фиксируем в отчёте как «доработку стандарта».

## 3.3. Сравнение `access.conf` и `sudoers`

| Критерий | `access.conf` | `sudoers` |
| :--- | :--- | :--- |
| **Что регулирует** | **Можно ли войти** на хост | **Что можно делать** после входа |
| **Когда срабатывает** | При входе (SSH, консоль, su) | При вызове `sudo` |
| **Кто читает** | `pam_access.so` (через `common-account`) | `sudo` (напрямую) |
| **Формат** | `действие:пользователи:откуда` | `кто где=(от_кого) что` |
| **Группа** | `(group)` или `group` | `%group` |
| **«Всё»** | `ALL` | `ALL` |
| **Отрицание** | `-` в начале строки | `!` перед командой |
| **Порядок важен** | ✅ да (первое совпадение) | ✅ да (последнее совпадение для `!`) |

**Ключевое различие:**
- `access.conf` — «**пускать или нет**» (бинарно).
- `sudoers` — «**что разрешено**» (список команд).

**Аналогия:**
- `access.conf` — охранник на входе: «тебя нет в списке — не пущу».
- `sudoers` — пропускной режим внутри: «тебе можно в этот кабинет, но не в тот».
